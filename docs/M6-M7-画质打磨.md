## M6 动态模糊：按真实快门做时间积分

### 之前错在哪

旧实现把「同一时刻前后几帧叠起来」，权重是三角形。两个问题：

1. **等效曝光只有一半**。真实快门是一个宽度 W 的矩形窗，窗口内等权积分；三角权重相当于矩形再卷一次三角核，`∫tri = 0.5`，二阶矩比 2.0 —— 观感更像柔光镜，不是拖影。
2. **在 8-bit sRGB 上平均**。sRGB 是 gamma 编码，直接平均会系统性压暗（暗部权重被高估）。

### 现在的做法

```
窗宽 W = (快门角 / 360) / perPair          180° 且不补帧 → W = 0.5 帧
积分区间 [t, t+W]                         锚定帧起点 ⇒ t+W ≤ 1 恒成立
每个样本 = 光流把相邻两帧 warp 到该时刻，再按 (1-s)·A + s·B 混合
输出 = 窗内 m 个等距样本的算术平均（中点法则，对盒核无偏）
```

- 因为窗口锚在帧起点、且 `W ≤ 1/perPair`，**积分永远不需要第三帧**，也不用第二条光流。
- 所有输出帧的积分区间等长 ⇒ 不会出现「清晰帧/模糊帧」交替闪烁。
- 累积在**线性光**里做：`decodeSRGB` 4096 段查表 → 求和 → `encodeSRGB`（sqrt 索引，误差 < 1e-4 码）。往返对 0…255 全部码值误差为 0。
- `m` 不是固定的：按 32×32 块、4 px 步长探一遍光流幅值 `D = |v|·flowScale·W`，取 `m = ceil(D)`（上限由「采样预算」档位给）。静止画面 `m = 1`，几乎零额外开销；快摇才堆到预算上限。
- 阶梯残差随 `m` 增大收敛：`m ≥ D` 时一个像素内采样点连续覆盖，误差精确为 0。

### 一处妥协：亮度转换走纯 Swift

vImage 的 ImageMatrixMultiply_ARGB8888ToPlanar8 在 Swift 里参数标注版本差异大（CI 首轮直接报参数个数不匹配），为了不再赌 API 签名，亮度平面改成纯 Swift 定点循环 (54R+183G+19B+128)>>8。4K 一帧多花几十毫秒，相对逐帧 AI 重建（100–400 ms）可以忽略，换来的是确定性。

### 成本（A15 级，`research/m6/RESEARCH.md` 实测口径）

| 场景 | 平均采样 | 每帧额外 |
| --- | --- | --- |
| 静止 / 三脚架 | 1.0 | ≈ 0 |
| 手持轻微晃（θ=180°） | 1.6–2.2 | 64–154 ms |
| 快速横摇（θ=360°，压到预算） | 10 | 400–700 ms |

另加光流 12–18 ms。`blurLight` 缓冲 16.8 MB（1.4MP 输出），峰值约 45 MB。

### 参数

- **快门角** 90° / 180° / 270° / 360°。180° 是电影标准（半帧曝光），360° 等于整帧曝光、拖影最长。
- **采样预算** 4 / 10 / 20 次每像素上限。越高拖影越平滑，耗时近似线性增长。
- 开了模糊输出上限降到 1440 长边 / 1.4MP：线性光缓冲在 4K 会到 99 MB，不值。

### 硬边界

模糊是低通，**已经糊掉的细节不可恢复**；MTF = |sinc(πfL)|，空间频率 `f = 1/L` 处直接归零。想要「拖影但主体清晰」，正确做法是提高帧率再合成，而不是靠后期反卷积。

## M7 细节增强：亮度域、钳制、抖动

### 旧 3×3 USM 的三个可测缺陷

| 问题 | 实测 |
| --- | --- |
| 核和 244/256（未归一化） | 全片亮度 **−4.6%**，`amount=0.25` 时更明显 |
| 无 halo 抑制 | 硬阶跃白边 **8 → 28 码** |
| 无噪声门控 | σ=3 的噪声被同倍放大 |

### 现在的做法

1. **亮度域**：`L = (54R + 183G + 19B) >> 8`，锐化只动亮度增量 `delta`，最后三通道同加 ⇒ 灰阶、中性灰逐位不变，不出彩边。
2. **保边低频**：5-tap 二项式 `[1,4,6,4,1]/16` 得到 `base`（比盒式更接近高斯，不会把细节当低频吃掉）。
3. **软门限噪声控制**：`d = L − base`，`t0 = 1.5 + 1.5·dn`、`t1 = 3 + 9·dn`，`knee = smoothstep((|d|−t0)/(t1−t0))`，`m = 1 − dn·(1−knee)`。小残差判为噪声压掉，大残差判为细节保留。
4. **边缘衰减**：源 5×5 动态范围 `rng`，`ew = 1/(1 + 0.25·(rng/32)²)`，高对比边缘少锐化，避免「越锐越脏」。
5. **钳制到源 5×5 极值 `[lo, hi]`**：这一步让 halo 在数学上恒等于 0 —— 硬阶跃最坏情况 28 码 → **0 码**，中调棋盘越界的 `[75,165]` → 严格 `[100,156]`。同时锐度没丢（10–90% 边缘宽度 3.38 px，旧实现 3.45 px）。
6. **4×4 Bayer 抖动**：量化前加 `(k+0.5)/16 − 0.5`（±0.47 码、零均值），锚定全局坐标，所以分条处理不会在条边界留下图案。
7. **分条处理**：64 行一条、重叠 4 行，5 张平面 ≈ 1.32 MB@4K，不整帧另开 66 MB 中转。

### 抗闪烁（仅 AI 逐帧超分时）

旧版是全局 0.22 权重 + 光流线性降权，静止区不够稳、运动区还会拖。

```
k = (still + (moving − still)·min(1, mag/ramp)) · 1/(1 + (ΔY/24)²)
still  = 0.20 + 0.60·af      → 静止区最高 0.80
moving = 0.16 − 0.10·af      → 运动区 0.06
```

再乘一个「对齐后亮度差」闸门：切镜、遮挡、光照跳变时权重掉到 0.008，几乎不融合，不出残影。`stable` 缓冲改成 A/B 乒乓，`inout` 永远写到「既不是上一帧、也不是当前帧」的那块 —— 顺带修掉旧代码每帧整帧 COW（4K 每帧白抄 33 MB）。

### 一处妥协：亮度转换走纯 Swift

vImage 的 ImageMatrixMultiply_ARGB8888ToPlanar8 在 Swift 里参数标注版本差异大（CI 首轮直接报参数个数不匹配），为了不再赌 API 签名，亮度平面改成纯 Swift 定点循环 (54R+183G+19B+128)>>8。4K 一帧多花几十毫秒，相对逐帧 AI 重建（100–400 ms）可以忽略，换来的是确定性。

### 成本

`applyDetail` 1080p ≈ 5–9 ms、4K ≈ 21–35 ms；`blendTemporalAdaptive` 1080p ≈ 4–7 ms、4K ≈ 15–25 ms。相对逐帧 AI 4× 重建（100–400 ms/帧）只占 2–8%。

### 没有换缩放核

`vImageScale` 默认核就是 Lanczos，会振铃；实测 4× 降采样 lanczos3 只比 box 多 0.69 dB，却在阶跃上产生 4 码振铃。自写 6-tap 可分离核在 4K 要 100 ms+/帧，不划算。这条留在文档里，避免以后有人以为是漏做。
