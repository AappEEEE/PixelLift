## 1. 真实相机在积分什么

### 1.1 快门角

摄影机的曝光时长不是用秒描述的，而是用**快门角** θ 描述它占一个帧间隔的比例：

```
T_exp = (θ / 360) / fps_source
```

180° 是电影标准 —— 曝光占半个帧间隔，所以 24fps 时 T = 1/48 s。θ=360° 是"整帧曝光"，
传感器从头积到下一帧开始，这是老式旋转快门机械极限，也是很多监控/运动相机的常态。

### 1.2 曝光积分的数学形式

忽略透视与旋转，只考虑局部匀速运动 v（像素/秒），场景辐亮度 S 在曝光窗内被传感器累积：

```
I(x) = (1/T) ∫_0^T S(x - v·τ) dτ
```

换成归一化时间 u = τ/T：

```
I(x) = ∫_0^1 S(x - v·T·u) du
```

也就是说：**运动模糊 = 沿运动方向、长度为 L = |v|·T 的盒式（box）低通**。
盒式滤波的频率响应是一维 sinc：

```
MTF(f) = |sinc(π f L)| = |sin(π f L) / (π f L)|
```

第一个零点在 f = 1/L。拖影长度 8 像素时，8 像素周期的细节被完全抹掉 —— 这就是
为什么拖影区域的锐化/超分信息必然丢失，后期不可能凭空恢复（除非有第二帧做光流合成，
也就是本设计在做的事）。

### 1.3 为什么不能"取几帧平均"

`(S(t1)+S(t2)+S(t3))/3` 在时间上是三个狄拉克函数的和，不是一段连续积分：

- 频率响应变成 `(1 + 2cos(...))/3` 这种带旁瓣的东西，拖影会出现**重影**（ghosting）
  而不是连续拖影；
- 采样点少时，拖影亮度台阶明显（S5 的实测：0.25 样本/像素时台阶达 25.5 码）；
- 采样点在帧中心（而不是均匀铺满曝光窗）时，等效窗宽也错了。

正确做法是**在曝光窗内做数值积分**：把 [0,1] 切成 m 段，每段取中点，等权求和。
步长 1/m，误差是 O(1/m²)（中点法则），而且对盒式核**无偏** —— 任意 m 都给同一个
平均亮度，只影响平滑度，不影响模糊量。这一点 S3.4 和 S6 都验证了：m=1..64 能量误差
恒等于 0.00e+00。

## 2. 权重：矩形（等权）还是三角

旧实现用三角权重：

```
w_j = max(0.08, 1 - |x_j| / (half + 0.5)),   x_j = j - (N-1)/2
```

`docs/M6-M7-画质打磨.md` 的理由是"等权平均会出现台阶"。这个理由在当前采样数下不成立，
而三角权重有一个致命副作用。

### 2.1 三角权重 = 矩形窗再卷一个三角核

真实快门是矩形窗。离散化之后仍然应该是矩形（等权）。如果对矩形窗再卷一个三角核，
得到的就是三角窗。这等价于**把场景先按三角核模糊一次，再做快门积分** —— 相当于
镜头本来就带一层柔光。

### 2.2 等效曝光时长只有一半（实测）

归一化窗宽为 1 时：

```
∫ rect = 1.0000                     ← 正确
∫ tri  = 0.5000                     ← 三角核的面积只有峰值的一半
∫tri / ∫rect = 0.5000
```

见 `verify_blur_math.py` 的 S2 输出。也就是说：**旧实现的模糊量只有真实快门的一半**，
并且拖影两端被 `1-|x|` 压暗，中间亮、两头淡 —— 看起来"更柔"，但那不是快门，是柔光镜。

想把模糊量补回来，只能把窗宽加倍；可窗宽一旦超过真实曝光窗，就开始在时间上偷帧，
出现"曝光超过 180°"的伪影。

### 2.3 二阶矩（拖影的"硬度"）

```
var_rect = W²/12 = 0.08333        （W = 1）
var_tri  = W²/24 = 0.04167
比值 = 2.000
```

三角核的高频衰减更狠（sinc² 而不是 sinc），视觉上就是"更糊、更没劲"。

**结论：用等权矩形窗。**每个样本自身的连续相位插值（`synthesize` 里的 `(1-t)·a + t·b`
双线性混合）已经提供了足够的平滑，不需要再叠一层三角核。

## 3. 线性光：这一步不能省

### 3.1 错在哪

传感器累积的是**光**（线性量），而 8-bit sRGB 是**光的 2.4 次方**。直接在码值域平均，
等于在做 `gamma(平均)` 而不是 `平均(gamma)`：

```
正确：  code = oetf( (1/m) Σ eotf(code_i) )
错误：  code = (1/m) Σ code_i
```

两者在 50% 覆盖率附近差得最狠。

### 3.2 实测偏差

单一覆盖率 f 扫描（S3.1）：

```
最大偏差 73.2 码 @ f = 0.244
  正确 135.5 码  vs  直接平均 62.3 码
```

73 个码值 —— 这不是"稍微暗一点"，是拖影明显发灰发暗。

彩色物体还会偏色（S3.3）：橙色条 [0.90, 0.35, 0.20] 在 25% 覆盖率下，

```
真实归一化 RGB  [1.000, 0.640, 0.484]
直接平均        [1.000, 0.656, 0.508]
最大码值差 69.6 码，归一化色相偏移 0.0232
```

灰阶不会偏色（三通道同值 → 通道间差 0.000e+00，S3.2），偏色只发生在**彩色边缘**，
但那正是运动物体最显眼的地方。

### 3.3 快速近似：两张 4096 段 LUT

```
decodeTable[i] = eotf(i / 4096),              i ∈ [0, 4096]     ← 线性插值查表
encodeTable[k] = oetf((k / 4096)²),           k ∈ [0, 4096]     ← sqrt 索引
```

- **解码**：`pos = code · 4096/255`，`i = floor(pos)`，`lerp(table[i], table[i+1], frac)`。
  4097 项、每项一次 `powf`，建表约 0.2 ms，之后每像素两次查表 + 一次乘加。
- **编码**：`pos = sqrt(y) · 4096`。为什么是 sqrt 索引：sRGB 编码在暗部斜率极大
  （y 从 0 到 0.003 时码值就从 0 跳到 12），等距索引会把分辨率浪费在亮部。用
  `pos = sqrt(y)` 相当于让表在**码值域**上近似等距，实测误差从 2e-4 降到 5e-5 码。

### 3.4 误差实测（S4）

```
解码 4096 段最大误差      0.00001 码
编码 4096 段最大误差      0.00005 码
256 个码值往返不一致数    0          ← 关键：静止像素必须逐字节复原
编码表单调性（降序段）    0
8 次累积后最大漂移        0.000 码
```

往返精确这一条很重要：它保证了 **8-bit 源自身的量化误差远大于 LUT 误差**，
所以"先转线性再转回来"不会引入可见损失，也就不需要把整条 HDR 管线改成 Float。

> 实现细节：`pos` 必须 clamp 到 `[0, n]`，`i` 再 clamp 到 `n-1`，否则 `table[i+1]` 越界崩溃。
> 用 `if !(pos >= 0.0) { pos = 0.0 }` 顺便吃掉 NaN（`NaN >= 0` 为 false）。

## 4. 采样密度：为什么是"1 像素一个样本"

离散积分把连续拖影切成 m 段，段长 = D/m 像素，D 是窗内总位移。段长太粗，
拖影边缘就会出现 m 级台阶（马赫带）。

### 4.1 实测台阶（S5，D = 20 像素的竖直边缘）

| m | 样本/像素 | 边缘最大残差 |
| --- | --- | --- |
| 2 | 0.10 | 63.75 码 |
| 4 | 0.20 | 25.50 码 |
| 5 | 0.25 | 25.50 码 |
| 10 | 0.50 | 12.75 码 |
| **20** | **1.00** | **0.00 码** |
| 40 | 2.00 | 0.00 码 |
| 80 | 4.00 | 0.00 码 |

关键不是"越多越好"，而是 **m = D（即 1 样本/像素）时残差精确归零**。原因是双线性
采样器本身就是一个 1 像素宽的 tent 核：当样本间距恰好等于 1 像素时，m 个 tent 的
和精确等于连续盒式积分（对阶跃边缘而言是解析相等的，不是近似）。所以：

```
m_b = ceil(D_b / stepPixels),   stepPixels = 1.0
```

再往上加样本（40、80）**没有任何收益**，只是白烧 CPU。这条准则就是成本模型的基石。
64 像素的长拖影用 m=64 时残差 0.032 码（S5 末项），依然干净。

### 4.2 分块自适应

- 块 32×32，块内按 4 像素步长探测 `|v|` 的最大值（抗噪，也省时间）；
- `D_b = |v|_max · flowScale · W`，`m_b = clamp(ceil(D_b), 1, 32)`；
- **m=1 的块完全跳过 LUT**，直接写字节 → 静止区域输出与原 `synthesize` 逐字节一致；
- 采样位置用分层中点 `(i+0.5)/m`，不做块间抖动。抖动会让相邻块相位不同，
  拖影上出现斜向条纹；m 相同时相位天然对齐，反而更干净。

为什么块与块之间看不到拼块：因为 m 是位移推出来的，不是质量档位。只要没被成本闸门压过，
每块的积分分辨率都恒等于 1 像素，块边界两侧输出连续。这是"按块自适应"能成立的前提，
也是它和"按块降质"的本质区别。

## 5. 窗锚点：为什么锚在帧起点

### 5.1 中心对称窗会越界

一对源帧 (a, b) 展开成 perPair 个输出帧，第 j 帧的相位是 `t = j/perPair`，
最大值 `(perPair-1)/perPair`。如果窗取 `[t-W/2, t+W/2]`：

- 最后一个输出帧需要 `t+W/2 > 1` 的样本 —— 那是**第三帧** b 之后的 c；
- 要么再算一条 b→c 的光流（成本翻倍），要么截断窗（拖影变短）。

### 5.2 锚在帧起点就永远不越界

窗取 `[t, t+W]`，其中

```
W = (θ/360) / perPair ≤ 1/perPair
```

于是

```
t + W ≤ (perPair-1)/perPair + 1/perPair = 1
```

**恒成立**（S1 实测 max(t+W) = 1.000000，扫了 θ ∈ {0,90,180,270,360} × perPair ∈ {1,2,3,4,5,8,16}）。
好处一次拿全：

1. 不需要第三帧 halo，不需要第二条光流；
2. 所有输出帧的积分区间等长 → 不会出现"清晰帧/模糊帧"交替闪烁（这是中心窗截断的典型病症）；
3. θ=360° 时相邻输出帧的窗首尾相接：`[0,W],[W,2W],...`，相邻窗间隙实测 0.000e+00 ——
   100% duty cycle，正是 360° 快门在 60fps 下该有的样子。

代价是整条时间轴有一个恒定相位偏移 W/2 ≤ 半个输出帧。60fps 下 ≤ 8.3 ms，
低于人耳唇音不同步阈值（约 20ms），完全不可辨。

### 5.3 duty cycle 实测（S1）

```
180° → 0.500
270° → 0.750
360° → 1.000
```

## 6. 和补帧 / 慢动作不打架

`perPair` 是"一对源帧展开成几个输出帧"，由补帧倍率 / 慢动作倍率共同决定。
窗宽除以 perPair 之后：

```
W = (θ/360) / perPair
```

- **补帧**让 perPair 变大 → W 变小 → 每个输出帧只覆盖一小段曝光 → 60fps 的拖影正好是
  30fps 的一半（S1：W(30fps)=0.500、W(60fps)=0.250、比值 0.500）。物理上这就是对的：
  帧率翻倍，帧间隔减半，同样 180° 快门的曝光时长也减半。
- **慢动作**让 perPair 更大 → W 更小，但每一输出帧对应更短的**真实**时间，
  所以慢放后的拖影按银幕时间看反而更长 —— 和真实高速摄影机降格拍摄再慢放的效果一致。
- **W 与 outFps 无关**，只与角度、倍率有关。所以不需要在渲染器里再乘一个 fps 因子，
  也就不会出现"补帧 + 模糊 = 双重模糊"。

## 7. HDR 放在哪一步

结论：**累积发生在 8-bit RGBA、`SDRToHDR.writeP010` 之前**。

理由（按重要性排序）：

1. 源是 8-bit。SDR 源的量化步长本身就有 1/255 的误差，LUT 往返误差 5e-5 码，
   比源噪声小 4 个数量级，提前转 Float 没有收益。
2. 如果改成"先转 PQ/HLG 线性浮点再累积"，需要额外的 `tw*th*3*4` 字节缓冲（1.4MP 又是
   16.8MB），并且要改造 `SDRToHDR.writeP010` 的入参类型 —— 那是全项目最敏感的
   HDR 路径，动它风险远大于收益。
3. 模糊发生在"源像素域"，HDR 是**输出编码**的选择。把两步解耦，HDR 开关就不会影响
   模糊的数学正确性：线性光累积只关心 sRGB 传输函数，与最终 PQ/HLG 编码无关。

如果以后接入 10-bit HDR 源（P010 解码），正确做法是**跳过 sRGB 的 eotf，直接按
BT.2020 PQ 的 EOTF 建表**再累积，届时 `decodeSRGB`/`encodeSRGB` 需要参数化成一对传输函数。
这一点本版没做，因为当前只解 8-bit SDR 源。

## 8. 离线验证脚本

### 8.1 结构

`verify_blur_math.py` 用与 Swift 完全相同的常量（4096 段 LUT、stepPixels=1、blockSize=32、
maxSamples=32），逐条复刻：

| 组 | 验证内容 | 对应 Swift |
| --- | --- | --- |
| S1 | 窗不越界、duty cycle、360° 无缝、fps 归一化 | `makePlan` 的 W |
| S2 | 矩形 vs 三角的等效时长与二阶矩 | 权重决策 |
| S3 | sRGB 直接平均偏差、灰阶中性、色相偏移、能量守恒 | 线性光必要性 |
| S4 | 4096 段 LUT 精度、往返、单调性、累积漂移 | `decodeSRGB`/`encodeSRGB` |
| S5 | 沿轨迹离散积分的台阶残差 | `stepPixels` 与 `m_b` |
| S6 | 分块覆盖、avgM、成本闸门行为 | `blockPlan` |

### 8.2 伪代码（核心三段）

```python
# 1) 曝光窗积分：等权 m 个中点样本
def integrate(a, b, flow, t, W, m):
    acc = zeros_like(a)
    for s in range(m):
        ph = t + W * (s + 0.5) / m          # 分层中点
        acc += synthesize(a, b, flow, ph)   # 连续相位插值
    return acc / m

# 2) 线性光累积
def accumulate_linear(samples):
    acc = 0.0
    for code in samples:
        acc += decode_LUT(code)             # 4096 段 + 线性插值
    return encode_LUT(acc / len(samples)) * 255

# 3) 每块采样数
def block_samples(flow, W, step=1.0):
    return [max(1, ceil(max_flow_in_block * W / step))
            for block in blocks(32)]
```

## 9. 故意没做的三件事

1. **Metal compute shader**。GPU 版本预计快 5–10 倍，但要新增 `.metal` 文件、在
   `project.yml` 里加 Metal 编译阶段、写 pipeline state，而本机没有 Xcode，
   一次编译失败就要来回 push 一轮。第一版用 CPU 标量 + `UnsafeBufferPointer`
   （`-O` 下已经能跑到约 2 亿像素级操作/秒），先保证能编过、结果对。
   GPU 化的接口已经预留好（`compose` 是纯函数，输入输出都是 `[UInt8]`/`[Float]`）。
2. **单帧反卷积去模糊**。用 2D 维纳/RL 反卷积能把单帧的拖影"猜"回来一点，但拖影是
   信息丢失（sinc 有零点），遮挡区无从恢复，还会在边缘产生振铃。Topaz 的做法是训练
   网络做时序合成，那需要模型，本 App 没有。这里走的是"把时间轴上的真实信息积分起来"，
   和相机快门同构，是唯一不靠猜的路。
3. **4K 模糊**。`blurLight` 在 4K 会到 99MB，加上其它缓冲必然 OOM。要做得改成条带
   （按 512 行一条，条带间留 32 行 overlap 供光流采样），本版没做，见 INTEGRATION.md 风险 #6。

## 10. 已知局限（诚实清单）

| 局限 | 后果 | 为什么接受 |
| --- | --- | --- |
| 光流只有 960 长边 | 细节位移估计有 0.2–1 像素误差 | `VNGenerateOpticalFlowRequest` 在 1080p 上跑满分辨率要 60ms+，性价比太低；误差会被 1 像素的 tent 采样吸收一部分 |
| 光流在遮挡边界必然错 | 拖影里有局部重影 | 物理上遮挡区确实没有信息，任何光流方案都有；θ 调小可缓解 |
| 成本闸门会压采样 | 极端运动下拖影出现 M 级台阶 | 只在 θ=360° + 全屏快摇时触发；不压的话一帧要 2 秒以上 |
| 块自适应有理论边界 | gate 生效时可能看到 32px 块界 | gate 不生效时积分分辨率恒为 1px，边界连续；缺省预算 10 在典型素材上不会触发 |
| 8-bit 输入 | 拖影在极暗区有量化台阶 | 源本身只有 8-bit，转 Float 累积不增加信息；LUT 往返误差 5e-5 码 |
| 无运动时零模糊 | 三脚架镜头完全不动 | 这是对的：真实相机对着静止场景也不会产生拖影 |
