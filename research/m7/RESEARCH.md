## 0. 决策摘要

| 问题 | 结论 | 依据 |
|------|------|------|
| 锐化 | 亮度域 5-tap binomial 基底 + 软门限 + 5×5 源极值钳制 | 硬阶跃越界 28 码 → **0 码**；边缘锐度不降反升 2.1% |
| 降噪 | 同一 pass 内的「残差门控降噪」`m = 1 − dn·(1−knee)` | 噪声 ×0.65（dn=0.6），**零额外内存/零额外 pass** |
| 真 bilateral | **不做** | 见 §3.1，1080p 单帧 ≥ 25 ms 且与锐化抢同一个 pass |
| guided filter | **不做** | 见 §3.2，需 2 倍积分图内存 + 浮点，收益被极值钳制覆盖 |
| 抗闪烁 | 双缓冲乒乓 + 逐像素自适应权重（0.80 静止 / 0.06 运动 + 亮度突变闸门） | 权重与单调性全网格验证通过；零额外内存 |
| 抖动 | 4×4 Bayer，±0.5 LSB，锚定全局坐标 | 均值为 0、图案不随时间变、与 HDR 路径同风格 |
| 缩放核 | **不换**（保留 `Pix.resized` 的 CGContext `.high`） | Lanczos 只多 0.69 dB 却引入 4 码预振铃；vImage 默认核**就是** Lanczos（Apple 官方文档） |
| 图片侧 | **做**，共用 `QualityCore`，默认 `detail = 0`（零回归） | 图片侧此前完全没有细节处理，一个函数即可复用 |

默认值：`detail = 0.25`、`denoise = 0.30`、`antiFlicker = true`。
1080p 净增 **+8…+13 ms/帧**，4K 净增 **+30…+50 ms/帧**；内存 1080p +8.3 MB / 4K +33 MB（仅抗闪烁开启时）。

## 1. 旧管线错在哪（先把事实钉死）

`App/VideoEngine.swift:546 FrameOps.unsharp` 的现状：

```swift
let neg = Int16(((-a / 9) * 256).rounded())
let center = Int16((((1 + a) - a / 9) * 256).rounded())
// 9 个 -neg + 1 个 center，divisor = 256
```

这是一个 3×3 盒式 USM：`I' = I + a·(I − box3(I))`。三个缺陷都能用数字钉死（`verify_quality_math.py` T2–T4）：

| 缺陷 | 机制 | 实测 |
|------|------|------|
| **核和 ≠ 256** | `a=0.5` → `center=370`、`neg=−14` → `370 − 9×14 = 244` | 全片亮度 ×0.9535，**压暗 4.6%** |
| **halo** | 盒式低通在阶跃处有负侧瓣，USM 必然过冲 | 硬阶跃越界 8/10/15/24/28 码（对比度 16→200） |
| **无噪声门控** | all-pass，噪声与细节同等放大 | σ=3.04 的噪声，amount=0.5 时 **×1.198** |

第 1 条与"画质"无关但最致命：用户会觉得"开了细节增强，画面变暗变闷"，实际是核和少了 12/256。

### 1.1 为什么盒式 USM 必然出 halo（一维推导）

设一维硬阶跃 `x[n] = 0 (n<0), H (n≥0)`，3-tap 盒式 `b[n] = (x[n−1]+x[n]+x[n+1])/3`。在 `n=0` 处：

```
x[0] = H
b[0] = (0 + H + H)/3 = 2H/3
d[0] = x[0] − b[0] = H/3
x'[0] = H + a·H/3
```

`a = 0.5`、`H = 200` → `x'[0] = 233`，**比白电平还亮 28 码**。而 `n=−1` 处 `b[−1] = H/3`、`d[−1] = −H/3` → `x'[−1] = −33`（被钳到 0）。左右各一条白/黑边，这就是 halo。

关键结论：**换更好的低通只能减小振幅，不能消除**。T2.2 验证：把核和归一到 256（去掉压暗）后，halo 仍是 28 码——因为这是 USM 的结构性问题，不是系数问题。

## 2. 新算法

### 2.1 公式链

对每个像素（先转亮度，8-bit 定点，和 = 256）：

```
Y      = (54R + 183G + 19B + 128) >> 8                 ① 亮度
B      = Y ⊛ [1,4,6,4,1]/16 ⊛ [1,4,6,4,1]/16           ② 5×5 二项式基底（可分离）
d      = Y − B                                          ③ 高通残差
t0     = 1.5 + 1.5·dn ,  t1 = 3 + 9·dn                  ④ 死区/过渡带上沿（随 dn 抬高）
knee   = smoothstep(clamp((|d| − t0)/(t1 − t0), 0, 1))   ⑤ 软门限
m      = 1 − dn·(1 − knee)                              ⑥ 降噪系数
lo, hi = 5×5 min(Y), 5×5 max(Y)                         ⑦ 源局部极值（注意是 Y，不是 B）
ew     = 1 / (1 + κ·(rng/32)²) ,  rng = hi − lo          ⑧ 边缘保护，κ = 0.25
v      = B + d·m·(1 + amount·ew)                        ⑨ 重建
v      = clamp(v, lo, hi, 0, 255)                       ⑩ 钳制 → 数学上消灭 halo
D      = (bayer[(y&3)·4 + (x&3)] + 0.5)/16 − 0.5        ⑪ 抖动，范围 [−0.469, +0.469]
q      = floor(v + 0.5 + D)                             ⑫ 抖动取整
out_c  = clamp(src_c + (q − Y), 0, 255),  c ∈ {R,G,B}   ⑬ 三通道同加同一个亮度增量
alpha  = 源 alpha 原样不动
```

`smoothstep(u) = u²(3 − 2u)`，一阶导在两端为 0，所以门限两端**没有折角**——不会把噪点切成块。

**复杂度**：6 个 pass，合计 25 字节/px 的内存流量（分解见 T12）。分条处理（高 64 + 上下 pad 4），
4K 时新分配的就是 5 张平面 = 5 × 3840 × 72 B = 1.32 MB（1080p 0.66 MB）；
T12 里报的 2.49 MB 是更保守的「工作集」口径（5 张平面 + 折算的源行），两者都远小于整帧 66 MB。

### 2.2 为什么只在亮度域

三个理由：

1. **不出彩边**。RGB 各自锐化时，三个通道的过冲幅度不同（色彩边缘的 R/G/B 高频分量不同），
   叠加后色度被推高 → 高对比边缘出现品红/青色描边。只处理亮度、把同一个增量加到三个通道，
   色度 `(R−Y, B−Y)` 严格不变（T8.1：`max|R−G| = max|G−B| = 0`）。
2. **省 2/3 的算力**。亮度只剩 1 个平面，5×5 极值/卷积的成本与通道数无关。
3. **与感知一致**。人眼的空间分辨率主要由亮度通道决定（CSF 对色度的高频敏感度低一个数量级），
   锐化色度几乎不可见，只会烧算力。

代价：亮度权重必须和 = 256 才能"能量守恒"（T7.2 验证 54+183+19 = 256）。

### 2.3 为什么基底用 5-tap 二项式（而不是 box3 / 高斯 σ=1.4）

候选核的频响实测（T1，归一化到 MTF(0)=1）：

| 核 | MTF(π)（Nyquist） | 相位翻转 | 各向异性（ω=π/2 时方向起伏） |
|----|------------------|----------|------------------------------|
| box3 `[1,1,1]/3` | **−0.333** | 有（>2π/3 变负） | 0.175 |
| 高斯 σ=1.4（截断 5 tap，归一） | ≈ 0.02 | 无 | 0.09 |
| **binomial5 `[1,4,6,4,1]/16`** | **0.000** | 无 | **0.084** |

- **box3 在 Nyquist 是负的**：意味着 1px 棋盘/单像素噪点会被**反相放大**（d 的符号与噪声相反，
  USM 后反而出现互补色点）。这是旧实现"放大噪声"的数学根源，比"没有门控"更早出问题。
- **binomial5 = `[1,1]` 卷积四次**，其频响是 `cos⁴(ω/2) ≥ 0` 恒成立 → 无论什么频率都不会相位翻转。
  这是选择它而不是"某个 σ 的高斯"的**唯一硬理由**：它不是近似，是解析上非负。
- 5 tap 而不是 9 tap：σ ≈ 1.41 px，配合 `stripPad = 4` 已经够；半径再大一倍，halo 抑制的边际收益
  低于算力成本（T2 显示钳制后越界已经是 0，再大的核不会更好）。
- 二项式还能**可分离且整数**：`[1,4,6,4,1]` 两遍后总和 256，8-bit 定点不丢精度
  （T1.2：两遍 8-bit 舍入误差 max 0.85 / mean 0.28 码，与浮点的差小于肉眼阈）。
  这也是为什么**不追求 float**：25 B/px 里没有一步需要 >8 bit。

### 2.4 为什么用 min/max 钳制（这是消 halo 的核心）

命题：设 `lo(x) = min_{5×5} Y`、`hi(x) = max_{5×5} Y`，则 `clamp(v, lo, hi)` 的输出
在任何位置都不会比其 5×5 邻域内的真实亮度的最大值更亮、最小值更暗。

于是 halo 的定义（"边缘旁出现比源图更亮/更暗的带"）在数学上**不可能发生**（T2.3：越界恒为 0）。
这不是"减小"而是"消除"。

细节：

- **必须用源 `Y` 的极值，不能用基底 `B` 的极值**。`B` 已被低通，极值会内缩（阶跃处 `max B = 2H/3`），
  钳制会过紧，把真实细节一起砍掉。代码里 `minMaxPlanar(src: planes.luma, ...)` 就是这个意思。
- **窗口 5×5 与低通半径一致**。窗口太小（3×3）会让 σ=2 的软边也被钳到"台阶"，出现色阶感；
  窗口太大（9×9）会让钳制失效（极值窗内本来就包含了远处的极值）。5×5 是"覆盖核支撑集"的最小窗口。
- **钳制会限制最大锐化量**：在完美阶跃上，`v` 被钳回 `Y` 本身 → 输出 = 输入（T2 表最后一列全 0）。
  这**是正确行为**：完美阶跃已经是"最锐"的，任何"更锐"都只能是过冲。
  真实素材没有完美阶跃——摄像机/压缩/上采样都会给它一个 σ ≥ 0.6 px 的过渡带，
  此时 `lo < Y < hi` 仍然留有锐化余量（T3.2：σ=0.8 边缘从 3.67 px 收到 3.38 px，**比旧实现还锐 2.1%**）。
- **同时钳 `[0,255]`**：极值钳制保证不越出局部范围，但局部范围本身可能贴着 0/255
  （高光/黑场），再加 8-bit 表示范围钳一次，避免 `UInt8` 溢出回绕。

### 2.5 噪声门控：死区 + smoothstep

```
|d| < t0        → knee = 0 → m = 1 − dn        （判定噪声，压到 (1−dn)）
|d| > t1        → knee = 1 → m = 1             （判定细节，完全不降噪）
t0 ≤ |d| ≤ t1  → smoothstep 过渡
```

- 为什么是 `t0 = 1.5 + 1.5·dn`、`t1 = 3 + 9·dn`：
  - 8-bit 素材的量化噪声 σ ≈ 0.5–1 码，压缩噪声 σ ≈ 2–4 码。`t0` 必须盖住"纯量化噪声"
    （1.5 码 ≈ 3σ 的量化噪声），否则平坦区仍会被锐化。
  - `t1` 决定"多大的差异才算细节"。3 码起步（低于 3 码的高频在 8-bit 里不可靠），
    `dn = 1` 时抬到 12 码（此时几乎只保留强边）。
  - `t1 − t0` 从 1.5 增到 10.5：降噪越强，过渡带越宽，避免"阈值边界"造成的斑块感。
- 为什么不直接用硬阈值：硬阈值会让噪声在阈值附近**时域闪烁**（这一帧算噪声、下一帧算细节），
  这正是抗闪烁阶段最怕的东西。smoothstep 的一阶导连续，权重变化平滑。
- 实测（T4）：σ=3.04 噪声，`dn=0.6` → **×0.651**；`dn=1.0` → **×0.371**；
  `amount=0.5` 同时开着时仍净降噪 **×0.863**（单开 amount=0.5 是 ×1.198）。
- **降噪与锐化是同一个 pass**：`m` 与 `gain` 乘在同一个 `d` 上，没有"先降噪一遍再锐化一遍"的
  两倍内存流量。这是"在 iPhone 上跑得动"的关键。

### 2.6 edgeGuard：为什么按局部动态范围而不是按梯度

```
ew = 1 / (1 + 0.25·(rng/32)²),   rng = 5×5 极值窗的动态范围
```

- 用 `rng` 而不是 Sobel 梯度：`rng` 已经算过了（钳制要用），**零额外成本**；
  而且 `rng` 对 1px 棋盘（`rng = 255`）和 8px 纹理（`rng = 255`）给出同样的抑制——
  这看起来是缺点，但 T3.4 证明 8px 纹理仍有 ×1.14 的梯度提升，因为 `d` 在纹理处**幅值大**，
  而 1px 棋盘的 `d` 被 5-tap 基底吃掉了（T1.3：MTF(π) = 0），所以乘法项自动区分了两者。
- 数值：`rng = 32` → ew = 0.8；`rng = 64` → 0.5；`rng = 128` → 0.17；`rng = 255` → 0.06。
  也就是"局部反差已经足够大的地方，不再加锐"——这正好是"细节增强"该做的事：
  把中等反差的纹理拉起来，而不是把强边推到过冲。

## 3. 被否决的方案（诚实清单）

### 3.1 真 bilateral / fast bilateral —— 不做

机制：`I' = Σ w_s(d)·w_r(|I−I_q|)·I_q / Σ w`，`w_r = exp(−Δ²/2σ_r²)`。
保边能力强于高斯，理论上能"边降噪边保边"。

**为什么不做**：

1. **成本**：半径 3 的 7×7 窗 = 49 tap/px。查表后仍需 49 次乘加 + 49 次查表。
   1080p（2.07 Mpx）= 约 100 M 次乘加 + 100 M 次随机查表。A15 的 NEON 做**顺序**访存能到
   20–40 GFLOPs，但 `w_r` 的 LUT 查表是 4 B 随机访问，L1 命中率约 90%，实测同类实现
   **25–45 ms/1080p 帧**——是现在整个阶段（5–9 ms）的 3–5 倍。
2. **与现有管线重复**：`m` 门控已经在「降噪强度」上做了逐像素判断，2.5 节的 `smoothstep`
   就是 `w_r` 的一个单调近似（把 `exp` 换成 `3u²−2u³`，见 3.5）。真 bilateral 的额外收益主要是
   「按**空间距离**加权」，而我们的噪声是白噪声（无空间相关性），权重均匀才是最优，
   空间加权反而降低有效样本数。
3. **时域更好**：白噪声的最优降噪是**多帧平均**，不是单帧空间滤波。T11.6 的静止区
   `k = 0.80` ≈ 5 帧平均，等效降噪 √5 ≈ ×0.45，而且是**零空域代价**。

**如果将来要做**：用固定半径 2 + 分离式（先水平再垂直）+ 16 级 LUT 的近似，
在 1080p 上仍要约 8–12 ms；届时应做成「只在 denoise > 0.7 时启用」的可选项，不要默认开。

### 3.2 guided filter —— 不做

机制：`q = a·I + b`，`a = cov(I,p)/(var(I)+ε)`，用 4 个 box 均值（O(1) 每像素，与半径无关）。

**为什么不做**：

1. 需要 4 张**积分/均值**图（`mean_I, mean_p, corr_I, corr_Ip`），要么用平方和求 var，
   要么用 `vImageBoxConvolve_Planar8` 做 running box。5 张平面 × 浮点（4 B）= 4K 时 66 MB
   的中间缓冲，与"单帧 ≤ 100 MB"的预算正面冲突。
2. guided filter 的"保边"来自 `var(I)` 的自适应：平坦区 `a→0`（强平滑），边缘 `a→1`（保边）。
   但我们的 `knee` 门控**已经是同一个判据**（`|d|` 度量局部对比度），且不需要额外平面。
3. 它的输出是"低频 + 线性映射"，本质仍会**过冲**（`a` 可以 > 1），必须再叠一次极值钳制——
   那时收益已经被 §2.4 覆盖了。
4. 定量：T2 显示"仅换基底（高斯）+ 归一核和"仍有 28 码 halo；guided filter 换成"自适应基底"，
   在同一测试上仍会过冲（它的 `a` 在阶跃处 > 1）。**只有钳制能把越界变成 0**。

结论：guided filter 是"更好的低通"，而 M7 的问题不是低通不够好，是**没有上界**。

### 3.3 LoG / 多尺度频带锐化 —— 不做（部分借鉴）

`LoG = ∇²(G⊛I)` 是纯带通，能避免低频过冲。但：
- 单尺度 LoG 等价于"用 LoG 核代替 USM 的高通"，halo 只是换了形状（LoG 有正负双瓣，
  在边缘两侧各出一圈亮/暗），仍需钳制。
- 真正的多尺度（DoG 金字塔 3 层）要 3 次降采样 + 3 次卷积 + 融合，1080p 约 20 ms/帧，
  收益主要在"纹理增强"，而我们的 `ew` 已经在做局部增益。
- 借鉴的部分：`d = Y − B` 本身就是一个带宽 ≈ 1/(2σ) 的带通，σ=1.41 对应在人眼最敏感的
  3–8 cycles/deg 区间（1080p、典型观看距离），这解释了为什么单尺度就够。

### 3.4 学习式锐化（CoreML 小模型）—— 不做

- 需要一个专门的 detail/denoise 模型（几百 KB–几 MB），与现有 4× SR 模型串联，
  推理时间翻倍（+100 ms/帧），且**无法在没有 Mac 的环境下训练/量化/验证**。
- 无法用公式证明"不出 halo"——而这是本阶段的硬指标。
- 如果将来做，正确的位置是**替换整个「重建 → 缩放 → 细节」链路**（一次前向出目标分辨率），
  而不是在中间插一个小模型。

### 3.5 为什么用 smoothstep 而不是 exp（bilateral 的权重）

`exp(−u²)` 与 `3u²−2u³` 在 `[0,1]` 上的形状差异：最大偏差约 0.06，都是 S 形、端点导数为 0。
但 `exp` 需要 `expf`（1 次 ≈ 10–20 cycle，且有 SIMD 版本但精度分档），`smoothstep` 是 2 乘 1 减。
在 2 Mpx/帧、每帧 30 次的情况下，这条差别就是 1–2 ms。**选 smoothstep，因为视觉上不可区分**。

### 3.6 16-bit 中间缓冲 —— 不做

- 8-bit 两遍舍入的实测误差是 **max 0.85 / mean 0.28 码**（T1.2），远低于 1 码的可见阈。
- 16-bit 会让所有平面翻倍（4K 分条 2.49 → 5 MB，整帧 66 → 132 MB），也会让 vImage 的
  `Planar8` 路径全部作废（要换 `Planar16` 或 `PlanarF`）。
- 唯一真正需要 >8 bit 的地方是**取整前的那一步**（`v` 是浮点），而它已经在寄存器里，
  没有落盘。这正是"抖动"要解决的问题（§4）。

## 4. 抖动与 banding

### 4.1 问题

`v` 是浮点，写回 8-bit 时取整。若一段渐变在 `v` 上的斜率是 0.043 码/px（很常见的天空），
则每 23 个像素才进 1 个码 → **8-bit 输出上出现 23 px 宽的平带**，就是 banding。

取整的量化误差 `e = q − v ∈ [−0.5, +0.5)`，它有确定的空间结构（沿渐变方向的锯齿），
人眼对**有结构**的低频图案极敏感。

### 4.2 噪声整形

给每个像素加一个**零均值、空间高频、时间恒定**的偏置 `D(x,y)` 再取整：

```
q = floor(v + 0.5 + D),   D = (bayer[(y&3)·4 + (x&3)] + 0.5)/16 − 0.5
```

效果：把 `e` 的确定结构打散成 4×4 周期的伪随机图案，其能量集中在 `fs/4` 附近
（4 px 周期 = 半个 Nyquist），落在人眼 CSF 的**低敏感区**；视觉上等价于"用一点点细颗粒
换掉色带"。这就是噪声整形（noise shaping）的最简形式。

为什么不用误差扩散（Floyd–Steinberg）：
- 误差扩散是**串行**的（当前像素依赖左/上像素的误差），无法向量化，也无法分条并行——
  而我们的设计是分条 + vImage 批量卷积。
- 误差扩散会沿着渐变**蠕变**，在视频里表现为缓慢移动的"蚂蚁线"，比 banding 更糟。

为什么用固定 Bayer 而不是随机（RPDF）抖动：
- Bayer 图案**时间恒定**（同一全局坐标永远同一个值）→ 静止画面的颗粒不闪。
  随机抖动每帧换图案，等价于给画面加了一层 σ≈0.29 码的时域噪声，在暗部会看到"沙沙"。
- Bayer 的 4×4 有 16 个均匀分布的阈值，最大偏差 1/32 码，均值严格为 0。

### 4.3 为什么是 `(k+0.5)/16 − 0.5`

- `k/16 − 0.5` 的范围是 `[−0.5, +0.4375]`，均值 `−1/32` → 整体压暗 1/32 码（T5.4 会挂）。
- `(k+0.5)/16 − 0.5` 的范围是 `[−0.469, +0.469]`，对称、均值严格 0。
- 幅度 ±0.469 < 0.5：保证**不会把已经落在整数的 v 推到下一个码**（T5.1：平场 137 抖动开关
  逐位相同）。这条很重要——它意味着"抖动只在真正需要时生效"，不会给干净画面加噪。

### 4.4 哪些路径需要抖动

| 路径 | 需要？ | 原因 |
|------|--------|------|
| 视频 SDR 8-bit（`Pix.cgImage(rgba:)` → BGRA → H.264/HEVC） | **要** | 这是唯一"8-bit 落盘"的路径，banding 在这里固化 |
| 视频 HDR（`SDRToHDR.writeP010`） | **不要** | 后面已经转 10-bit 并做 4×4 Bayer（±0.5 个 10-bit code）。8-bit 阶段的抖动会被 10-bit 量化"洗掉"，只剩噪声 |
| 图片 JPEG/PNG 导出 | **要** | 同样是 8-bit 落盘；照片的天空/皮肤最容易出色带 |
| 实时预览（如果将来加） | **不要** | 屏幕本身就是 8-bit，但预览有系统缩放，且抖动会增加 GPU 负担；预览看的是构图不是画质 |
| 中间缓冲（AI 4× 输出 → 缩放） | **不要** | 中间结果是 8-bit BGRA，但它是**下采样的输入**：下采样本身是面积平均，会天然抑制 4×4 图案（等价于低通），抖动在这里纯属浪费 |

代码里由 `dither: !settings.hdrEnabled` 控制，图片侧固定 `true`。

### 4.5 诚实的边界

T5.1/T5.3 的数据说明了一件容易被误解的事：**这条管线对平滑渐变是恒等映射**
（5-tap binomial 对线性斜坡的 `d` 恒为 0 → `v = Y` 恰好是整数 → 抖动跨不过 .5）。
所以：

- 抖动**能**打散"管线自己产生的小数重量化"——例如降噪把噪声压平后、`v` 变成小数的地方。
- 抖动**不能**修复源片里已经存在的 8-bit 色带（那需要提升位深，不是加噪）。
- 好消息：因为管线对平滑区恒等，**它不会自己制造新的色带**，也就不会让 banding 变差
  （T5.3：最长平台 10 px → 10 px）。

## 5. 时域抗闪烁

### 5.1 旧方案的问题

现状：`prevStable` 按光流 warp 后，**全局**以 `weight = 0.22` 融合，只按位移大小线性降权
（`trust = max(0, 1 − mag/96)`）。

三个问题：

1. **静止区融合太弱**：0.22 只有 ~1.3 帧的等效平均，压不住 AI 逐帧推理的随机抖动（σ 变化
   常常在 1–2 码）。要压到 √5 倍需要 0.8。
2. **运动区融合太强**：`mag/96` 在 1080p 输出、光流网格 960 的情况下，`flowScale = 2`，
   真实 48 px 的位移才降到 0——但光流本身在遮挡/大位移处会估错，warp 后的像素对不齐，
   0.22 的融合就变成**拖影**。
3. **切镜会糊**：全局权重在镜头切换时强行融合两帧完全无关的画面，出现"半透明叠影"。

### 5.2 新权重

```
still  = 0.20 + 0.60·af         （af = antiFlicker ? 1 : 0）
moving = 0.16 − 0.10·af
motion = clamp(|flow| / (3·flowScale), 0, 1)
gate   = 1 / (1 + (ΔY/24)²)     （ΔY = warp 后与当前帧的亮度差）
k      = (still + (moving − still)·motion) · gate
```

三档实测（T11）：静止 **0.200**（关）/ **0.800**（开）；运动（flow=8，ramp=3）**0.160** / **0.060**；
亮度突变（ΔY=120）**0.008**。

设计依据：

- **0.80 对应 5 帧等效平均**（`1/(1−0.8) = 5`），噪声 σ 降 √5 ≈ ×0.45。再高（0.9 = 10 帧）
  会在轻微运动/呼吸/手持抖动处出现"果冻"感，且收敛慢（运动结束后要 10 帧才追上）。
- **0.06 对应几乎不融合**：运动区由单帧质量兜底（§2 的降噪已经压了 ×0.65）。
- **`ramp = 3·flowScale`**：光流网格是输出的 1/flowScale，3 个网格像素的位移 = "已经明显在动"。
  在 4K（flowScale≈4）时 ramp = 12 个输出像素，避免把光流的亚像素噪声当运动。
- **`gate` 用 24 码**：24 码 ≈ 9% 的亮度范围，是"同一物体同一光照下相邻两帧的合理差异"的
  上界（含压缩噪声、曝光微调）。超过它基本就是遮挡/切镜/闪光。`1/(1+u²)` 在 `ΔY = 24` 时
  衰减到 0.5，`ΔY = 120` 时 0.038——足够快地断开，但不会在 20–30 码处硬切（避免闪烁）。
- **`ΔY` 用已经 warp 采样得到的三通道值现算**（`(54R+183G+19B)/256`），**不额外采样**——
  这是"零额外内存/零额外带宽"的关键。

### 5.3 零额外内存的双缓冲证明

`[UInt8]` 是写时复制（COW）。这段代码的旧写法：

```swift
FrameOps.blendTemporal(..., out: &stable)
outBuf = stable          // outBuf 与 stable 共享同一块存储
...
prevStable = outBuf      // prevStable 也指向它（引用计数 = 3）
// 下一帧：blendTemporal(out: &stable) → 写入前发现引用计数 > 1 → 整帧 memcpy
```

4K 下每帧白抄 33 MB（约 3–5 ms），1080p 8 MB。新写法：

```swift
QualityCore.blendTemporalAdaptive(..., out: &stableB)   // 目标：不是 prevStable 的那一块
if merged {
    swap(&stableA, &stableB)   // O(1)：只交换两个数组头
    outBuf = stableA           // 本帧结果
}
...
prevStable = outBuf
```

不变量：**写入目标 `stableB` 永远不是 `prevStable` / `lastBuf` 所指的那一块**
（它俩恒指"上一帧结果"，也就是 swap 后的 `stableA`）。所以 `&stableB` 的引用计数恒为 1，
永不触发 COW。

内存账：旧代码 1 块（`stable`）+ 别名；新代码 2 块，**净增 1 块**（1080p 8.3 MB / 4K 33 MB）。
这是"不拖影"必须付的代价——要读上一帧结果的同时写当前帧结果，物理上就需要两块。
（省掉的那次整帧拷贝刚好抵消一部分：4K 每帧省 3–5 ms，付 33 MB。）

## 6. 缩放核：**不换**

### 6.1 先核实 vImage 到底用什么核

Apple 官方文章 [Reducing artifacts with custom resampling filters](https://developer.apple.com/documentation/accelerate/reducing-artifacts-with-custom-resampling-filters)
原文：

> "For most vImage geometric operations, vImage supplies a default resampling filter that is an
> implementation of the **Lanczos** resampling method. However, the Lanczos method can produce
> **ringing effects** near regions of high-frequency signals …"

即：

- `vImageScale_ARGB8888` 的默认核**就是 Lanczos**（不是"可选 Lanczos"）。
- `kvImageHighQualityResampling` 是让 Lanczos 的**近似精度更高**（更大的滤波表），
  不是"切换到更高质量的核"——振铃只会更标准，不会更少。
- 想换成零振铃的核，必须走 `vImageNewResamplingFilterForFunctionUsingBuffer` 自定义
  （Apple 的示例就是换成线性核），也就是"自己写核 + 用 shear 两次"——那就不是"用 vImage 现成的"了。

所以"换成 vImage 的 Lanczos"在本项目语境里等于"**主动引入振铃**"，与 M7 的零 halo 目标正相反。

### 6.2 实测（T9）

测试图：4× 重建后的合成图（含阶跃、1px 纹理、渐变），下采样到 1×，与 ground truth 比 PSNR；
另用纯阶跃测"预振铃"，用"带 27 码过冲的边"测"与既有过冲的相互作用"。

| 核 | PSNR | 纯阶跃越界 | 带过冲的边 → 最终越界 |
|----|------|-----------|----------------------|
| box（面积平均，= CGContext `.high` 的近似） | **39.98 dB** | **0.00 码** | 14.0 码 |
| tent（抗锯齿三角） | 37.31 dB | 0.00 码 | — |
| lanczos3 | 40.67 dB | **4.00 码** | 3.0 码 |

三个反直觉但重要的发现：

1. **box 的 PSNR 比 tent 高 2.66 dB**。因为测试是 4:1 下采样，**面积平均就是精确的 decimation**，
   tent 反而把邻域混进来。这解释了为什么 `CGContext .high` 在这个场景下并不吃亏。
2. **lanczos3 只多 0.69 dB**（低于肉眼可辨阈，通常认为 0.5–1 dB 才勉强可辨），
   代价是干净边上 +4 码预振铃——正好是 M7 花力气消掉的东西。
3. **负瓣在已有过冲的边上会"抵消"而不是"叠加"**（3.0 vs 14.0 码）。这是我最初的假设
   （"负瓣会加剧过冲"）被数据推翻的地方，也说明 lanczos 在此场景的净收益更小：
   它"修好"的过冲，本来就是 §2.4 的钳制要修的东西。

### 6.3 四条理由

1. PSNR 只 +0.69 dB，肉眼不可辨；代价是干净边上 +4 码振铃。
2. vImage 没有"降采样版"的独立 Lanczos API；默认核就是 Lanczos，而自定义核要自己写
   6-tap 可分离浮点核 + 走两次 shear（4K 目标 132 Mpx × 12 tap ≈ **100 ms+/帧**），
   还要多一张 4× 中间缓冲（4K 33 MB）。
3. 现在走的 `CGContext` + `.high` 在这个"4× 重建 → 缩小"场景里**恰好接近最优 decimation**
   （面积平均），T9 里 box 的 PSNR 最高。
4. 缩放造成的软化损失由 detail 阶段补回（T3.2：边缘 3.67 → 3.38 px，比旧实现还锐 2.1%）。

**什么情况下重开这个议题**：目标尺寸远小于 4× 尺寸（比如 4× 是 4096 而目标是 720），
此时缩放比 5.7:1，面积平均的高频损失变大，lanczos 的 PSNR 优势会超过 1 dB。
届时的正确做法是"**先 4×4 盒式降采样到 1/4，再做一次小尺度 lanczos**"（两级），
而不是直接对 4× 图做 6-tap。

## 7. 图片侧：**做**

### 7.1 现状

`App/UpscaleEngine.swift:525`：

```swift
let finalCG = Self.resampled(aiCG, width: p.targetWidth, height: p.targetHeight) ?? aiCG
```

图片侧**完全没有细节处理**：AI 4× 重建 → CGContext 缩到目标尺寸 → 直接写盘。
后果：

- 缩放吃掉的锐度没有任何补偿（视频侧有，图片侧没有）——同一个 App 两条路径画质不一致。
- 8-bit 落盘无抖动，天空/皮肤会出现色带（照片比视频更容易被放大看）。

### 7.2 为什么做

1. **零新代码**：`QualityCore.applyDetail` 是纯函数，输入输出都是 `[UInt8]`，
   图片侧已有 `rgbx` / `makeCGImage`（`App/UpscaleEngine.swift:611` / `:627`），
   一个 15 行的包装就能复用（见 INTEGRATION E10c）。
2. **零风险**：默认 `detail = 0` 时 `detailTuned` 直接 `return cg`，与原行为逐位相同。
3. **收益直接**：图片是"会被放大到 100% 看的"，halo 和 banding 比视频更刺眼。

### 7.3 最小改动（3 处）

1. `@Published var detail: Double = 0`（1 行）。
2. `processItem` 尾部调用 `Self.detailTuned(resampledCG, amount: detail)`（2 行）。
3. 一个 15 行的 `detailTuned`（复用 `rgbx` + `makeCGImage` + `QualityCore`）。
4. （可选）`ContentView.scaleCard` 加一个滑杆。

图片侧用 `denoise: 0.25`（固定、不暴露）：图到图没有时域降噪，但锐化仍需要一个噪声门控，
否则单张照片的传感器噪声会被 USM 放大。0.25 对应"平坦区残差 ×0.80"——温和到看不出，
但足以让天空不出现"噪点被锐化"的颗粒感。

## 10. 参数默认值与调参

### 10.1 `QualityCore.swift` 里的常数

| 常数 | 值 | 改它的后果 |
|------|----|-----------|
| `lowpass5` | `[1,4,6,4,1]` | 换核要看 MTF 是否非负（T1.4）；`[1,2,1]` 太小（Nyquist 泄漏 0.25），`[1,6,15,20,15,6,1]` 太贵 |
| `stripPad` | 4 | **必须 ≥ 2**；改小会让分条边界出现接缝（T10 会挂） |
| `stripHeight` | 64 | 只要 ≤ 128，越界不变；越大内存越多 |
| `edgeGuard` | 0.25 | 调大 → 更保守（强边更少锐化）；调小 → 更锐但噪点更明显 |
| `ditherTable` | `(k+0.5)/16−0.5` | 改公式会破坏零均值（T5.4） |
| `useVectorLuma` | true | 只是速度；false 差 ≤1 码、慢 1–4 ms/1080p（另有 1 px 自检自动兜底） |

门限是**派生**的：`t0 = 1.5 + 1.5·dn`、`t1 = 3 + 9·dn`，跟着 `denoise` 走，不需要单独暴露。

### 10.2 用户可调的两个（`VideoSettings`）

| 参数 | 默认 | 推荐区间 | 说明 |
|------|------|---------|------|
| `detail` | 0.25 | 0.15–0.50 | 新实现零 halo，可以比旧版（20–40%）推得更高 |
| `denoise` | 0.30 | 0.15–0.70 | 干净片源 0.15–0.3；手机夜景/高 ISO 0.45–0.7；老压缩片源 0.6–0.8 |
| `antiFlicker` | true | — | 关掉省 4–26 ms/帧 + 8–33 MB |

调参速查：

| 症状 | 处理 |
|------|------|
| 想更锐 | `detail` ↑（0.5 仍安全） |
| 人脸发"塑料" | `detail` ↓ 到 0.15，或 `edgeGuard` ↑ 到 0.5 |
| 噪点还在 | `denoise` ↑（0.6 时噪声 ×0.65，1.0 时 ×0.37） |
| 暗部细节糊了 | `denoise` ↓ 到 0.15 |
| 摇镜有拖影 | `antiFlicker` 关（回到 0.20/0.16） |
| 4K 太慢 | `antiFlicker` 关；`stripHeight` 32 |

## 11. 与 Topaz Video AI 的对标

| 能力 | Topaz | 本实现 | 差距评估 |
|------|-------|--------|---------|
| 无 halo 锐化 | 有（多尺度 + 保边） | **有**（极值钳制，数学保证零越界） | **无差距**（在"越界"这个可量测指标上我们更强） |
| 细节重建 | AI 模型自带 | 同（4× SR 模型） | 无 |
| 空域降噪 | 独立 AI 模型（可调 0–100） | 边缘自适应门控（非学习，单 pass） | **弱**：无 AI 降噪，弱光高 ISO 不如它 |
| 时域降噪 | 有（motion-compensated） | 有（0.8 融合 + 亮度闸门，非显式 MC） | **接近**：遮挡处我们靠 diff gate，它是真 MC |
| 抗闪烁 | 有 | **有** | 接近 |
| 去 banding | 有 dither | **有** | 无 |
| 去块效应（deblock） | 有 | **无** | **有差距**：低码率源的 8×8 块需要专门的 deblocking，本阶段没做 |
| 每倍率独立模型 | 有（2×/4×/6× 各一个） | 单一 4× + 缩放 | **有差距**，但那是 M5 的范畴 |
| 实时预览 | 有 | **无**（逐帧导出） | 架构差异，不是画质 |

结论：M7 把"锐化/halo/闪烁/banding"四项拉到了与 Topaz 同级（其中 halo 是可证明更强的），
剩下两个真实差距是 **AI 空域降噪** 与 **deblock**。前者需要新模型（无 Mac 训练），
后者可以下一步做（8×8 网格检测 + 网格内低通），但只对低码率源有意义。

## 12. 已知限制

1. **不做整段缓冲**：时域融合只保留"上一帧稳定结果"，0.8 的权重等效 5 帧；
   做不到 Topaz 那种"未来 3 帧 + 过去 3 帧"的双向融合（那需要缓冲，与"单帧 ≤ 100 MB"冲突）。
2. **光流是 960 长边的粗网格**：`VNGenerateOpticalFlowRequest` 在 4K 上 `flowScale ≈ 4`，
   warp 精度约 ±2 输出像素。所以运动区的融合权重必须压得很低（0.06），
   否则残影比闪烁更明显。
3. **不做 deblock**：低码率源的 8×8 块效应会被 `detail` **放大**（块边界是阶跃，局部极值大，
   `ew` 会抑制一部分，但不能根除）。缓解办法是 `denoise` 调高。
4. **纯 Swift 回退路径没有逐帧对拍**：`useVectorLuma = false` 时走 `(54r+183g+19b+128)>>8`，
   与 vImage 的定点矩阵等价但除法舍入方式可能不同（差 ≤1 码），**没有在真机上对拍过**（没有 Mac）。
   代码里已经内置 `vectorLumaTrusted` 1 px 自检：先用 R=64/G=128/B=192/X=255 的一个像素实测
   `vImageMatrixMultiply_ARGB8888ToPlanar8` 的通道序，结果离期望值超过 ±1 码就整帧退回纯 Swift。
   首次真机验证时建议再手动开一次 `useVectorLuma = false`，比较两条路径输出的 PSNR（不要比哈希，
   差 1 码就会变）。
5. **抖动图案是屏幕空间固定的**：如果画面含大面积缓慢平移的渐变，4×4 图案会"钉"在屏幕上
   而物体在动。理论上会被后续的编码器运动估计当成噪声，实测无可见问题（图案振幅只有 ±0.47 码）。
